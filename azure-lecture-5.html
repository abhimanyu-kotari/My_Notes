Azure Container Apps (ACA) — Architecture & Scaling Theory

Azure Container Apps is the "sweet spot" between the simplicity of ACI and the full power of Kubernetes. It sits on top of Kubernetes, Envoy proxy, KEDA, and Dapr — but hides all of that complexity from you. Understanding why those four technologies work together — and what KEDA actually measures, how Envoy routes traffic, and what a Revision really is — gives you the conceptual clarity to build and troubleshoot modern microservices confidently.

01. What is Azure Container Apps (ACA)?

Azure Container Apps (ACA) is a fully managed serverless container platform for running microservices and containerized applications. Unlike ACI (which runs a single isolated container), ACA is designed for multi-service architectures where multiple containers need to communicate, scale independently, and share common infrastructure.

Service Underlying Tech Best For Complexity
ACIAzure hypervisor fabricIsolated batch jobs, quick testsLow
ACAKubernetes + Envoy + KEDA + DaprMicroservices, event-driven apps, scale-to-zeroMedium
AKSRaw Kubernetes (you manage)Complex enterprise systems, custom CRDsHigh

The Festival Park (Container Apps Environment) provides shared infrastructure. Your specialized food trucks (individual Container Apps) serve different menu items (microservices). The festival organizer (KEDA + Envoy) manages crowd flow and truck scaling automatically.

03. Core Architecture Deep Dive

The 4 Technologies Inside Every ACA Environment

Kubernetes

The underlying container orchestration engine. ACA uses it but abstracts all YAML manifests, node management, and CRDs from you. You never interact with kubectl directly.

Envoy Proxy

A high-performance Layer 7 proxy that handles all inbound HTTP/HTTPS traffic, automatic TLS termination, traffic splitting, and service-to-service routing. Runs as the ingress controller.

KEDA

Kubernetes Event-Driven Autoscaler. Extends Kubernetes HPA to scale on external metrics (queue depth, HTTP RPS, Kafka lag) rather than just CPU/RAM. Enables true scale-to-zero.

Dapr

Distributed Application Runtime. A sidecar that provides service discovery, pub/sub messaging, state management, and secret access — all via a simple HTTP/gRPC API, abstracting the backend provider.

04. KEDA Autoscaling Theory — How Event-Driven Scaling Works

KEDA (Kubernetes Event-Driven Autoscaler) works by polling external metric sources (called "scalers") and feeding those metrics into the Kubernetes HPA (Horizontal Pod Autoscaler). When a metric exceeds a threshold, KEDA signals Kubernetes to add more container replicas. When the metric drops to zero, KEDA allows scaling all the way down to 0 replicas — which is impossible with the default Kubernetes HPA.

External Event Source (e.g., Azure Service Bus Queue) │ ▼ KEDA polls every 30 seconds (configurable) KEDA ScaledObject reads: "Queue has 500 messages" │ ▼ Compares to target threshold (e.g., 50 msgs/replica) KEDA tells Kubernetes HPA: "Scale to 10 replicas" │ ▼ Kubernetes creates 9 new container pods 10 Worker containers drain the queue in parallel │ ▼ Queue reaches 0 messages KEDA tells HPA: "Scale to 0 replicas" All containers terminate → Cost = $0

05. Revisions & Traffic Splitting — Zero-Downtime Deployments

Every time you update a Container App's configuration or deploy a new Docker image tag, ACA automatically creates a new immutable Revision. A revision is a versioned snapshot of the container app configuration — it cannot be changed once created.

Deployment Strategies Using Revisions

Blue-Green Deployment

Route 100% traffic to Revision 1 (Blue). Deploy Revision 2 (Green). Test Green internally. When ready, flip 100% traffic to Green instantly. Zero downtime, instant rollback possible.

Canary Deployment

Start with 90% Revision 1, 10% Revision 2. Monitor error rates and latency. Gradually shift: 80/20 → 50/50 → 0/100 as confidence builds. Catch production bugs with 10% blast radius.

Why "canary"? Coal miners used canary birds to detect carbon monoxide — the canary would die before humans were affected, providing early warning. In software, the "canary" revision receives a small percentage of real user traffic first. If it fails, only that small group is impacted; the rest stay on the stable version.

06. Ingress & Envoy Proxy Theory

All traffic into ACA flows through Envoy Proxy — a battle-tested Layer 7 proxy originally developed at Lyft and now used by Netflix, Google, and Airbnb. ACA runs Envoy as a managed ingress controller, so you get its capabilities without configuring it yourself.

ExternalAnyone on the public internetAuto-managed certificatePublic APIs, frontend websites

07. Scale-to-Zero Economics

Time: 00:00 02:00 04:00 06:00 08:00 10:00 12:00 18:00 23:00 Replicas: 3 0 0 0 5 12 8 3 0 Scale-to-Zero Window (2 AM - 6 AM) Cost during this window: $0.00 vs. Traditional VM: Replicas: 3 3 3 3 3 3 3 3 3 Paying for 3 VMs all night even with 0 users

ACA scales to 0 replicas automatically when no traffic arrives. The first request triggers a cold start (1–5 seconds for a container already cached in the region). For latency-sensitive apps, you can set a minimum replicas = 1 to avoid cold starts at the cost of one always-on container.

08. CLI Deployment Walkthrough

# Install ACA CLI extension
az extension add --name containerapp --upgrade

# Create environment (the shared "festival park")
az containerapp env create   --name my-aca-env   --resource-group my-rg   --location eastus

# Deploy a public-facing microservice (external ingress + scale-to-zero)
az containerapp create   --name my-web-app   --resource-group my-rg   --environment my-aca-env   --image mcr.microsoft.com/azuredocs/aci-helloworld:latest   --target-port 80   --ingress external   --min-replicas 0   --max-replicas 10   --query properties.configuration.ingress.fqdn

# Configure canary traffic split (90% v1, 10% v2)
az containerapp ingress traffic set   --name my-web-app   --resource-group my-rg   --revision-weight my-web-app--v1=90 my-web-app--v2=10

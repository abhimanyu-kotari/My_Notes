Azure Container Instances (ACI) — Theory & Concepts

Azure Container Instances answers a simple question: what if you could run a Docker container in the cloud without ever thinking about servers? No VMs to provision, no OS to patch, no cluster to manage. ACI achieves this through the serverless execution model — understanding why that works, what a Container Group is, how restart policies control container lifecycle, and why per-second billing changes economics completely.

01. What is Azure Container Instances (ACI)?

Azure Container Instances (ACI) is Microsoft Azure's pure serverless container runtime. It is the fastest way to run a container in the cloud — you provide a Docker image, specify CPU and RAM requirements, and Azure runs the container within seconds, with zero infrastructure management on your part.

Traditional Approach (Before ACI)

  1. Create an Azure Virtual Machine (3–5 min wait)
  2. SSH into the VM and run apt update
  3. Install Docker Engine on the VM
  4. Pull your Docker image
  5. Configure NSG firewall rules
  6. Run the container manually
  7. Keep paying for the VM 24/7, even when idle

With ACI (Serverless Containers)

  1. Provide: image URL, CPU, RAM, port
  2. ACI provisions everything in ~10 seconds
  3. Container is live with a public FQDN
  4. Pay only while the container is running
  5. Delete with one command — billing stops instantly

02. Serverless Execution Theory — What "Serverless" Actually Means

Serverless does not mean "no servers exist." Servers absolutely exist — you simply do not own, manage, patch, or provision them. Microsoft's Azure infrastructure manages a large pool of bare-metal servers. When you request an ACI container, Azure's control plane allocates resources from this shared pool on-demand, runs your container, and returns the resources to the pool when you're done.

The Core Serverless Value Proposition: You declare what you want to run (a container image), not where it should run (a specific server). Azure's orchestration layer handles placement, scheduling, health monitoring, and restart logic. This is called the "serverless abstraction."

Cold Start vs. Warm Start in ACI

Scenario What Happens Typical Time
Cold StartNo pre-warmed container. Azure must pull the image (if not cached), allocate resources, and launch the process from scratch.5–15 seconds
Subsequent RunsImage is cached in the Azure region. Resource allocation is faster because Azure pre-warms infrastructure.2–5 seconds

Note: ACI cold starts are measured in seconds (not milliseconds like a simple function), because launching a full container process is heavier than a function invocation. For sub-second cold starts, use Azure Functions instead.

04. Container Groups — ACI's Fundamental Resource Unit

In ACI, the top-level deployable unit is a Container Group — a collection of one or more containers that are co-scheduled on the same physical host machine. This concept is directly analogous to a Pod in Kubernetes.

Container Group: "web-and-sidecar" ├── Container 1: nginx (port 80) ← Main web server │ - Shares local network with Container 2 │ - Communicates via localhost:9090 └── Container 2: log-forwarder (port 9090) ← Sidecar pattern - Reads nginx access logs from shared volume - Ships logs to Azure Monitor Shared Resources within the group: ✓ Same lifecycle (start/stop together) ✓ Same localhost (containers talk via 127.0.0.1) ✓ Same storage volumes (mounted to both containers) ✗ NOT shared: CPU/RAM (each container has own allocation)
The Sidecar Pattern: The classic use case for multi-container groups is the "sidecar" architecture — a main application container paired with a helper container that handles cross-cutting concerns like logging, monitoring, or configuration refresh. The sidecar lives alongside the main container, sharing its network and storage, without modifying the main container's code.

05. Restart Policies — Matching Container Lifecycle to Your Workload

Policy Restart Trigger Ideal Use Case
Always (default)Restarts automatically on crash OR successful exit (exit code 0 or non-zero)Long-running web services, HTTP APIs, background queue listeners — anything that must stay up permanently
OnFailureRestarts only when the container exits with a non-zero (error) exit codeETL batch jobs, database backup routines, scheduled data transformations
NeverRuns exactly once to completion — never restarted regardless of exit codeOne-time migration scripts, CI/CD build agents, database seeding tasks
Billing implication of "Always" on a task container: If you run a data processing script with --restart-policy Always, ACI will restart it in a loop after each completion — costing you money indefinitely! Always use Never or OnFailure for one-shot tasks.

06. Per-Second Billing — The Economics of Serverless Containers

ACI uses per-second billing measured against allocated vCPU cores and GiB of memory. You pay only for the duration the container group is in a "Running" state.

Real Cost Example

A nightly ETL script running 1 vCPU + 1.5 GiB RAM for 8 minutes at approx. $0.000012/vCPU-second and $0.0000013/GiB-second:

vCPU cost: 1 core × 480 seconds × $0.0000012 = $0.000576 Memory cost: 1.5 GiB × 480 seconds × $0.0000013 = $0.000936 ───────────────────────────────────────────────────── Total: $0.001512 (~0.15 US cents per nightly job run) Compare to: Keeping a B1s VM running 24/7 = ~$7.59/month Your 30 nightly jobs = ~$0.045/month Savings: 99.4%

Key rule: ACI billing starts the moment the container group transitions to "Running" state and stops the moment you delete the container group or it exits (for Never restart policy). There is no charge for stopped or terminated groups.

07. Hands-On: Deploying ACI via Azure CLI

# 1. Create a Resource Group
az group create --name RG-ContainerDemo --location eastus

# 2. Deploy a container with a public DNS label
az container create   --resource-group RG-ContainerDemo   --name my-first-aci   --image mcr.microsoft.com/azuredocs/aci-helloworld   --dns-name-label myunique-student-demo   --ports 80   --cpu 1   --memory 1.5   --restart-policy Never

# 3. Check status and get the public URL
az container show   --resource-group RG-ContainerDemo   --name my-first-aci   --query "{Status:instanceView.state, URL:ipAddress.fqdn}"   --output table

# 4. View live logs
az container logs --resource-group RG-ContainerDemo --name my-first-aci

# 5. Delete the container (billing stops)
az container delete --resource-group RG-ContainerDemo --name my-first-aci --yes

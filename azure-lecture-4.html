Module 04 Azure ACI Serverless Containers Fast Spin-Up Batch Processing Per-Second Billing

Azure Container Instances (ACI)

What is this module about? The fastest and simplest way to run a Docker container in the cloud without managing any virtual machines, orchestrators, or clusters. Understanding Container Groups (Pods), restart policies, deploying via Azure CLI with DNS labels, and leveraging per-second serverless economics for batch jobs.
Why is this critical for engineers? Spinning up a full Kubernetes cluster for a 3-minute video-rendering job is wasteful and slow. ACI gives you instant, frictionless container execution that terminates the moment your job finishes.

01. What is Azure Container Instances (ACI)?

Before ACI, if you had a Docker container you wanted to test or run in the cloud, you had to:

  1. Provision an Azure Virtual Machine.
  2. SSH into the VM and install the Docker daemon engine.
  3. Pull your image and execute docker run.
  4. Remember to deallocate the VM so you don't get billed for idle compute.

Azure Container Instances (ACI) completely revolutionizes this workflow. It is a pure serverless container service. You pass your Docker image URL, specify how many vCPUs and gigabytes of memory you require, and Azure spins up and executes your container within 3 to 5 seconds! There are zero virtual machines to manage, zero operating system patches to install, and zero orchestration clusters to configure.

02. ACI vs. ACA vs. AKS Decision Matrix

Service Best Use Cases Orchestration & Autoscaling Management Overhead
ACI Short-lived batch jobs, nightly data pipelines, build runners, quick prototypes. None. Runs standalone isolated container tasks. Zero (Fully Serverless)
ACA Microservices, web APIs, event-driven queue processors, auto-scale to zero. Built-in KEDA autoscaling, revisions, traffic splitting, Envoy ingress. Low (Serverless Kubernetes)
AKS Complex enterprise ecosystems, service meshes, granular networking controls. Full native Kubernetes API (Deployments, StatefulSets, Ingress Controllers). High (Node pools, Kube upgrades)

03. Container Groups Architecture

The top-level resource in ACI is a Container Group. A Container Group is a collection of containers that are scheduled on the same host machine, sharing the exact same lifecycle, local network, and storage volumes.

AZURE CONTAINER GROUP ARCHITECTURE ('analytics-group')
Public IP: 20.198.44.12 Shared Localhost Bridge Shared Storage Volume Mount
📦 Primary Container Main App

Python Data Processor & Web API

Port: 8080

🛡️ Sidecar Container Helper

Log Shipper, Metrics & Prometheus Exporter

Port: 9090

Inter-container communication occurs via localhost:9090 ↔ localhost:8080 with zero network hops or latency.
💡 Kubernetes Analogy: A Container Group in ACI is the exact architectural equivalent of a Pod in Kubernetes.

04. Container Restart Policies

When launching an ACI container, you must configure its restart policy according to its workload type:

  • Always (Default): If the container process stops or crashes, ACI restarts it immediately. Ideal for continuous web servers and long-running APIs.
  • Never: The container runs its task once. When the script exits (Exit Code 0), the container stops and is never restarted. Ideal for one-time database schema migrations or batch reports.
  • OnFailure: The container runs once. If it crashes with an error (non-zero exit code), ACI retries execution. If it succeeds (Exit Code 0), it shuts down peacefully. Ideal for nightly ETL data extract scripts.

05. Deploying ACI via Azure CLI

Azure CLI / Bash 
# Step 1: Create a Resource Group
$ az group create --name my-rg --location eastus

# Step 2: Deploy a Public Web Container with DNS Name Label
$ az container create \
  --resource-group my-rg \
  --name my-aci-demo \
  --image mcr.microsoft.com/azuredocs/aci-helloworld:latest \
  --dns-name-label myuniqueappak2026 \
  --ports 80 \
  --cpu 1 \
  --memory 1.5 \
  --restart-policy Always

# Step 3: Check Container State & Public FQDN URL
$ az container show \
  --resource-group my-rg \
  --name my-aci-demo \
  --query "{FQDN:ipAddress.fqdn,State:instanceView.state}" \
  --output table

# Step 4: Stream Real-Time Logs
$ az container logs --resource-group my-rg --name my-aci-demo

# Step 5: Delete Container when finished
$ az container delete --resource-group my-rg --name my-aci-demo --yes

06. Per-Second Serverless Economics

Why do data engineering teams love ACI? Because of per-second granularity:

The Batch Job Calculation:

Imagine a machine learning image-processing container that runs for 4 minutes and 15 seconds (255 seconds) every night at midnight.

- With a standard Virtual Machine: You pay for the entire hour (or keep it running 24/7 if you forget to stop it).
- With Azure Container Instances (ACI): You are billed strictly for 255 seconds of allocated vCPU and RAM. The total nightly compute cost is less than $0.003 USD!

Projects, IAM Permissions & Service Accounts for AI Agents

What is this lecture about? This module dives into the architectural backbone of Google Cloud: Projects and IAM (Identity and Access Management). We explore how projects act as isolated security and billing boundaries, dissect the crucial differences between Project ID, Project Name, and Project Number, master the IAM formula (Principal + Role + Resource), and uncover how to create and govern Service Accounts—the "robot identities" used by your AI agents and Python code to securely access cloud databases, storage, and models without risking human credentials.
Why is this critical for engineers? In real-world enterprise development, AI agents operate autonomously. If you assign broad "Owner" privileges to an agent or leak your private JSON credentials on GitHub, rogue automated scripts or hacked code can wipe out production databases or rack up thousands of dollars in unauthorized compute.

01. The Google Cloud Resource Hierarchy

Everything you do in Google Cloud lives inside a strictly organized hierarchy, just like a multinational company:

🏢 Organization (e.g., yourcompany.com)
    └── 📁 Folders (e.g., Engineering, Data Science, Security)
         └── 📦 Projects (e.g., ai-rag-prod, gcloud-basics)
              └── ⚙️ Resources (Compute VMs, Cloud Storage Buckets, BigQuery Tables, Cloud Run Services)

The Project Sandbox Concept

Think of a Project as a labeled box or an isolated sandbox. It holds everything you build for a specific application:

  • Complete Isolation: Resources in Project A cannot communicate with or interfere with resources in Project B unless you explicitly configure VPC peering or authorized APIs.
  • Blast Radius Containment: If an intern accidentally runs a destructive script in test-project, your live production project is 100% untouched.
  • Granular Cost Accounting: Every invoice line item is tied to a specific project. You know exactly what your RAG chatbot cost versus your customer analytics pipeline.

02. Project ID vs. Project Name vs. Project Number

Every GCP project possesses three distinct identifiers. Confusing them is one of the most common beginner errors:

Identifier Who Sets It? Can It Be Changed? Global Uniqueness Usage & Examples
Project ID You (or auto-suffixed by Google) PERMANENT (NEVER!) Globally unique across the entire world gcloud-basics-504709
Used in 99% of CLI commands, APIs, and client libraries.
Project Name You Editable Anytime Does NOT need to be unique "GCloud Terminal Basics"
Friendly human display label on the web console.
Project Number Google Cloud internally Immutable Globally unique integer 482910481029
Used behind the scenes by Google service agents and IAM grants.
⚠️ Golden Rule: Project IDs are permanent. Once chosen and created, a Project ID can never be renamed. Choose clean, lowercase, hyphenated names (e.g., company-rag-prod-01).

03. Managing Projects via Console & CLI

1. Creating a Project via Web Console

Top Header Bar ➔ Project Dropdown ▾ ➔ Click "New Project"
  1. Enter your desired Project Name (e.g., AI Agent Studio).
  2. Review the auto-generated Project ID (or click Edit to pick your own unique ID).
  3. Select your Organization / Parent Folder (or leave as No organization for personal accounts).
  4. Click Create.

2. Creating a Project via `gcloud` CLI

bash 
# 1. Create a project with an explicit unique ID and a human-friendly display name
gcloud projects create gcloud-basics-2026 --name="GCloud Basics 2026"

# 2. List all projects accessible by your authenticated account
gcloud projects list

# 3. View detailed metadata (create time, state, project number)
gcloud projects describe gcloud-basics-2026

3. Setting the Active Working Project

Just like navigating into a folder with cd, you must tell gcloud which project your commands should target:

bash 
# Tell gcloud to target your new project for all subsequent commands
gcloud config set project gcloud-basics-2026

# Verify that your active project was updated
gcloud config list project

4. Configuring Application Default Credentials (ADC)

If you write Python code using the google-cloud-storage or google-cloud-bigquery SDKs, your code needs local credentials to run:

bash 
# Authenticates your local environment for Python/Node.js client libraries
gcloud auth application-default login

5. Linking Your Project to a Billing Account

bash 
# Get your Billing Account ID
gcloud billing accounts list

# Link your active project to the billing account
gcloud billing projects link gcloud-basics-2026 \
  --billing-account="012345-6789AB-CDEF01"

# Verify billing linkage
gcloud billing projects describe gcloud-basics-2026

04. IAM Core Architecture & The Mental Model

1. The Core IAM Formula

The Universal Security Formula:

WHO (Principal) + CAN DO WHAT (Role / Permissions) + ON WHICH (Resource)

2. The Hotel Keycard Analogy

Think of staying at a luxury hotel:

  • Guest Keycard: Opens only your assigned room door (e.g., Room 402) and grants elevator access to the gym. It does not open Room 403 or the manager's office.
  • Master Keycard: Held only by the hotel general manager for emergencies.
  • Housekeeping Staff Badge: Allows entry during morning hours to clean towels, but cannot access financial records at the front desk.

3. The Three Building Blocks of IAM

  1. Principal (The WHO):
    • Google Account (User): A real human email address (e.g., alice@gmail.com).
    • Google Group: A mailing list collection of users (e.g., data-scientists@company.com).
    • Service Account: A non-human "robot identity" for code and AI agents (e.g., ai-rag-agent@project.iam.gserviceaccount.com).
  2. Permission (The ATOMIC ACTION):

    Represented in service.resource.verb notation: storage.buckets.create, storage.objects.get, compute.instances.start.

  3. Role (The BUNDLE OF PERMISSIONS):

    You never assign raw permissions individually. You assign a Role, which is a curated package of dozens or hundreds of permissions.

4. Primitive Roles vs. Predefined Roles

Role Type Roles Scope & Risk Level Production Recommendation
Primitive / Basic Owner, Editor, Viewer Extremely Broad / Dangerous
Grants blanket access across almost every single GCP service in the project.		 ❌ AVOID IN PRODUCTION. Only project creators should have Owner. Never assign to teammates or scripts.
Predefined (Job-Based) roles/storage.objectViewer
roles/bigquery.dataEditor
roles/run.invoker		 Granular & Targeted
Crafted specifically for job duties (e.g., read files from Cloud Storage without permission to delete buckets).		 ✅ INDUSTRY STANDARD. Adheres strictly to the Principle of Least Privilege.
🔒 Principle of Least Privilege (PoLP): Always grant the absolute minimum permissions an engineer or agent needs to perform their task. If an AI agent only needs to read PDFs from a bucket, give it roles/storage.objectViewer. Never give it Owner or Editor out of laziness!

05. Managing IAM Policy Bindings with `gcloud`

An IAM Policy Binding attaches a Principal to a Role on a specific project or resource.

1. Inspecting Active IAM Policies

bash 
# View all users, service accounts, and roles bound to your project
gcloud projects get-iam-policy gcloud-basics-2026

2. Granting Access to a Teammate (Adding Policy Binding)

Let's grant read-only access to our Cloud Storage objects to a data analyst colleague:

bash 
# Grant the 'Storage Object Viewer' role to a specific user email
gcloud projects add-iam-policy-binding gcloud-basics-2026 \
  --member="user:analyst.colleague@gmail.com" \
  --role="roles/storage.objectViewer"

3. Revoking Access (Removing Policy Binding)

When an analyst finishes their project or leaves the team, clean up and remove the permission immediately:

bash 
# Revoke the role immediately
gcloud projects remove-iam-policy-binding gcloud-basics-2026 \
  --member="user:analyst.colleague@gmail.com" \
  --role="roles/storage.objectViewer"

4. Web Console Navigation for IAM

Navigation Menu ☰ ➔ IAM & Admin ➔ IAM ➔ Click "Grant Access"
  1. In the New principals field, type the colleague's email address.
  2. In the Select a role dropdown, search for the specific role (e.g., Cloud Storage ➔ Storage Object Viewer).
  3. Click Save. GCP immediately updates the policy.

06. Service Accounts: Robot Identities for AI Agents

1. What is a Service Account?

A Service Account is a special Google Cloud identity that represents an application, script, or AI agent rather than an individual human user.

It does not have a human password, cannot log in through a web browser with 2-factor SMS codes, and has an email address ending in:

Terminal Output 
[service-account-name]@[project-id].iam.gserviceaccount.com

2. Why AI Agents Must Use Service Accounts

  • Autonomous 24/7 Execution: AI agents running in production (e.g., automated customer support bots, document summarizers) must interact with BigQuery or Vertex AI without human intervention.
  • Poisoning & Prompt Injection Defense: If a rogue user injects a malicious prompt trying to make your LLM delete database records, the action will fail immediately with 403 Forbidden if the agent's service account was only granted read-only permissions!
  • Auditing & Traceability: Cloud Audit Logs clearly identify whether an API call was made by human alice@company.com or robot rag-extractor-sa.

3. Creating a Service Account via `gcloud` CLI

bash 
# 1. Create a service account for your AI agent
gcloud iam service-accounts create ai-storage-reader \
  --display-name="AI Agent Storage Reader"

# 2. List all service accounts in the project to verify creation
gcloud iam service-accounts list

4. Granting Least-Privilege Roles to the Service Account

bash 
# Bind the Storage Object Viewer role to the newly created service account
gcloud projects add-iam-policy-binding gcloud-basics-2026 \
  --member="serviceAccount:ai-storage-reader@gcloud-basics-2026.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer"

07. `key.json` Management & Security Protocol

1. What is `key.json`?

A Service Account Key is a downloadable JSON credential file containing a private RSA key. Your external Python code or local Docker container reads this file to prove its identity to Google Cloud:

bash 
# Generate and download a private key for your service account
gcloud iam service-accounts keys create key.json \
  --iam-account="ai-storage-reader@gcloud-basics-2026.iam.gserviceaccount.com"

Inside key.json, you will find structure similar to:

json 
{
  "type": "service_account",
  "project_id": "gcloud-basics-2026",
  "private_key_id": "893b1029c9284091823901",
  "private_key": "-----BEGIN PRIVATE KEY-----\nMIIEvgIBADANBgkqhkiG9w0BAQEFAASCBKgw...",
  "client_email": "ai-storage-reader@gcloud-basics-2026.iam.gserviceaccount.com"
}

2. Using the Key in Python Code

python 
from google.cloud import storage

# Point Google client libraries to your downloaded key file
import os
os.environ["GOOGLE_APPLICATION_CREDENTIALS"] = "key.json"

client = storage.Client()
buckets = list(client.list_buckets())
print("Connected successfully via Service Account!")

3. The #1 Security Catastrophe: Committing `key.json` to GitHub

🚨 NEVER, EVER COMMIT `key.json` TO GIT!
Automated bot scanners scrape public GitHub repositories 24/7 within seconds of any commit. If you accidentally push a key.json file to GitHub:
  1. Hackers extract your private key within 60 seconds.
  2. They spin up hundreds of massive GPU/CPU clusters in regions like US-Central and Asia to mine cryptocurrency.
  3. You can wake up to a $10,000+ cloud bill!
  4. Protection: Always add *.json and key.json to your .gitignore file before generating any key.

4. Revoking and Deleting Leaked Keys

If a key is ever compromised or no longer needed, delete it immediately:

bash 
# 1. List active keys for the service account
gcloud iam service-accounts keys list \
  --iam-account="ai-storage-reader@gcloud-basics-2026.iam.gserviceaccount.com"

# 2. Delete the key by its Key ID
gcloud iam service-accounts keys delete "893b1029c9284091823901" \
  --iam-account="ai-storage-reader@gcloud-basics-2026.iam.gserviceaccount.com"

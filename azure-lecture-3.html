Module 03 Docker Containerization Linux Namespaces cgroups Union FS Microservices

Docker & Containerization — Deep Theory

Why do containers exist? The answer lives deep inside the Linux kernel: namespaces isolate processes and cgroups cap their resources. Understanding these primitives — not just the CLI commands — is what separates engineers who use Docker from engineers who understand Docker. This module covers the theory from the ground up: environment drift, kernel isolation mechanics, the Union File System that makes images lightning-fast, and how every docker run translates to a Linux system call.

01. The "It Works on My Machine!" Crisis

Every software engineer eventually faces the same frustrating situation: code runs perfectly on a developer's laptop but crashes immediately in production or on a teammate's machine. This is called Environment Drift — the gap between two machines grows over time because each has different OS versions, library versions, environment variables, and system configurations.

Why does the same code behave differently?
  • Developer has Python 3.11; production server has Python 3.8.
  • Local Mac has libssl v3.0 baked into macOS; Linux server has libssl v1.1.
  • Developer forgot that a specific environment variable (DATABASE_URL) was set locally.
  • A compiled C extension was built for macOS ARM64 but needs x86-64 Linux.

Docker's answer: Stop shipping code. Start shipping environments. Package the application code, the exact runtime version, system libraries, OS user-space, and configuration into a single immutable binary artifact — a Container Image. If it runs in one environment, it runs identically everywhere.

02. Linux Kernel Isolation Theory: Namespaces & cgroups

Containers are not virtual machines. They are not a new invention of Docker. They are a composition of two Linux kernel features that have existed since 2002 and 2007 respectively. Docker simply made these kernel features easy to use.

Linux Namespaces (Isolation)

A namespace is a Linux kernel feature that wraps a global system resource and makes it appear as if each process has its own isolated instance of that resource.

NamespaceWhat It Isolates
pidProcess IDs — container's PID 1 is independent of host.
netNetwork stack (interfaces, routing tables, ports).
mntMount points and file system hierarchy.
utsHostname and domain name.
userUser and group IDs (UID/GID remapping).

cgroups (Control Groups — Resource Limiting)

cgroups (control groups) is a Linux kernel mechanism that limits, accounts for, and isolates the resource usage of a collection of processes — CPU, RAM, disk I/O, and network bandwidth.

ResourceWhat cgroups Controls
CPUMax CPU cycles a container process can consume.
MemoryRAM limit; OOM killer kills container if exceeded.
Block I/ODisk read/write throughput throttling.
NetworkBandwidth limits on the container's virtual NIC.
Key Insight: When you run docker run --memory=512m --cpus=1, Docker translates this into cgroup configuration. When you expose a port with -p 80:8080, Docker creates a network namespace and sets up iptables NAT rules automatically. You are not doing anything magical — you are using a well-designed API over mature Linux primitives.

Why containers are NOT full isolation like VMs: All containers on the same host share the same Linux kernel. If you run a container on Ubuntu but the host runs Ubuntu 22.04, the container uses the host's 22.04 kernel. This is why Docker on Windows and macOS requires a lightweight Linux VM (WSL2 or HyperKit) to run Linux containers — there is no native Linux kernel on those operating systems.

04. The Standard Cargo Shipping Container Analogy

The 1956 Revolution That Changed Global Trade:

Before standardized shipping containers existed, loading a cargo ship was chaos. Loose barrels, wooden crates, irregular machinery — dock workers had to hand-load every item individually. Unloading took weeks. In 1956, Malcolm McLean invented the standardized steel shipping container. The crane and ship do not care what's inside. The external dimensions and corner locks are always identical. It moves seamlessly from ship to train to truck with the same mechanical interface everywhere.

Docker does the exact same thing for software. Your container holds a Python Flask API, a Java Spring Boot app, or a Node.js microservice. Azure ACI, ACA, AKS, or any Kubernetes cluster on any cloud provider runs it with identical commands — because the container interface is standardized via the OCI (Open Container Initiative) specification.

05. The 4 Core Docker Pillars

↻ The Container Build-Ship-Run Lifecycle
1. Dockerfile

Plaintext recipe with build instructions. Defines the base OS, what software to install, what files to copy, and what command to run on startup.

FROM, COPY, RUN, EXPOSE, CMD
2. Docker Image

Immutable read-only binary artifact produced by docker build. Contains all layers (OS, libraries, app code). Can be versioned and shared globally.

docker build -t app:v1 .
3. Live Container

A running instance of an image. Docker adds a thin writable layer on top of the read-only image layers. 50 containers can run from 1 image simultaneously.

docker run -d -p 80:80 app:v1
4. Container Registry

A centralized cloud library for storing and distributing images. Docker Hub is the public registry. Azure Container Registry (ACR) is the enterprise private option.

docker push myacr.azurecr.io/app:v1

06. Image Layers & the Union File System — Why Images Are Efficient

A Docker Image is not a single monolithic blob. It is a stack of read-only layers, where each layer represents one instruction in the Dockerfile. This is managed by a Union File System (OverlayFS on modern Linux systems), which merges multiple directory trees into a single cohesive view.

Layer 0 (Base): FROM python:3.11-slim → ~45 MB (Python runtime + Debian slim) Layer 1: RUN pip install flask → ~8 MB (Flask + Werkzeug + Jinja2) Layer 2: RUN pip install gunicorn → ~1 MB (Gunicorn WSGI server) Layer 3: COPY requirements.txt . → ~2 KB (Dependency manifest) Layer 4: COPY . . → ~500 KB (Your application source code) Layer 5: CMD ["gunicorn", "app:app"] → ~0 KB (Metadata only — no files) ───────────────────────────────────────────────────── Total Image: ~55 MB (vs. a full Ubuntu VM: ~1 GB+) When you run this image: ┌─────────────────────────────────────────────────────┐ │ Writable Layer (Container) — ephemeral, deleted on stop │ ├─────────────────────────────────────────────────────┤ │ Layer 5: CMD instruction (read-only) │ │ Layer 4: App source code (read-only) │ │ Layer 3: requirements.txt (read-only) │ │ Layer 2: Gunicorn (read-only) │ │ Layer 1: Flask (read-only) │ │ Layer 0: Python + Debian base (read-only) │ └─────────────────────────────────────────────────────┘
Build Cache Efficiency: If you change only your app source code (Layer 4), Docker reuses all previous layers (0–3) from cache and only rebuilds Layer 4 onwards. This is why the best practice is to COPY requirements.txt . and RUN pip install before COPY . . — dependencies change rarely, code changes frequently.

07. Dissecting a Real Dockerfile — Line by Line

# 1. Base Image — the foundation everything builds on
FROM python:3.11-slim

# 2. Working directory inside the container's isolated filesystem
WORKDIR /app

# 3. Copy dependency manifest FIRST (exploits build cache)
COPY requirements.txt .

# 4. Install inside the image (not on your host machine!)
RUN pip install --no-cache-dir -r requirements.txt

# 5. Copy application source code (changes frequently)
COPY . .

# 6. Document which port the app listens on (metadata only)
EXPOSE 8000

# 7. Default command to execute when container starts
CMD ["python", "app.py"]
Instruction What It Does Creates New Layer?
FROMSets the base image — the starting operating environmentYes
WORKDIRSets the working directory for all subsequent instructionsYes
RUNExecutes a shell command during build time — installs softwareYes
COPYCopies files from host into the image filesystemYes
EXPOSEDocuments a port (does NOT actually open/publish it)No (metadata)
CMDDefault command at container start — overridable by docker runNo (metadata)

08. Port Forwarding Explained — Host ↔ Container Networking

By default, every container lives inside its own private net namespace — completely isolated from both the host network and other containers. If your web app listens on port 8000 inside the container, nothing outside can reach it without an explicit bridge.

User Browser: http://localhost:80 │ ▼ (Host Machine Network Interface — eth0) [ Host Port :80 ] │ ▼ Docker creates iptables NAT DNAT rule: │ DNAT :80 → 172.17.0.2:8000 ▼ [ Container Virtual NIC — net namespace ] │ ▼ [ App Process: python app.py listening on :8000 ]

The -p 80:8000 flag tells Docker: "Create a NAT rule so that any TCP packet arriving on the host's port 80 is forwarded to the container's internal port 8000." This is handled by Linux iptables DNAT rules, automatically managed by the Docker daemon.

09. Essential Docker CLI Cheatsheet

Build & Images

docker build -t myapp:1.0 .
docker images
docker rmi myapp:1.0
docker pull nginx:latest

Run & Manage

docker run -d -p 80:8000 --name site myapp:1.0
docker ps          # running only
docker ps -a       # all containers
docker stop site
docker rm site

Debug & Inspect

docker logs -f site        # live logs
docker exec -it site bash  # shell inside
docker inspect site        # full JSON metadata
docker stats               # live resource usage

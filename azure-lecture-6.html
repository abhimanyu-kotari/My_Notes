Azure Blob Storage — Theory, Architecture & Concepts

Blob Storage is not just "cloud file storage." It is a massively distributed object storage system architected for exabytes of unstructured data with eleven-to-sixteen nines of annual durability. Understanding the theory behind object storage vs. block storage, how the LRS/ZRS/GRS redundancy hierarchy protects against failures at different physical scopes, the cryptographic anatomy of a SAS token, and how lifecycle rules automate cost optimization — this is the knowledge that separates an Azure user from an Azure architect.

01. What is Azure Blob Storage?

Azure Blob Storage is Microsoft's massively scalable object storage service for the cloud. The word "BLOB" stands for Binary Large OBject. It stores any type of digital file — images, videos, audio, PDFs, ML training datasets, server logs — in native binary format without requiring disk formatting or partitioning.

Unlike a traditional file system where you navigate folders and files, Blob Storage uses a flat namespace. Every blob has a unique URL:

https://<storage-account-name>.blob.core.windows.net/<container>/<blob-name> Example: https://mycompanystorage.blob.core.windows.net/user-uploads/profile-photo-1049.jpg ↑ ↑ ↑ Storage Account Container Blob (file)

02. Object Storage vs. Block Storage vs. File Storage

Dimension Object Storage (Blob) Block Storage (Managed Disks) File Storage (Azure Files)
AbstractionKey-Value store: URL → binary blobRaw disk blocks (like a physical hard drive)POSIX-style directory tree (SMB/NFS mount)
Access MethodHTTP REST API (GET/PUT/DELETE)Attached to a single VM (read/write like local disk)Mounted via network share (accessible by multiple VMs)
ScalabilityVirtually unlimited (exabytes)Up to 32 TB per diskUp to 100 TiB per share
Best ForMedia files, backups, ML datasets, static websitesVM OS disks, databases (SQL Server data files)Shared config files, legacy apps needing shared network drive

03. The Amazon Fulfillment Warehouse Analogy

🏢
Storage Account

The entire warehouse building with its unique address and security checkpoint. One account per region per project.

📂
Container

An organized aisle or section inside the warehouse (e.g., "user-avatars", "invoice-pdfs", "system-logs").

📦
Blob

The individual package on the shelf. Can be tiny (1 KB text file) or massive (1 TB video archive).

Storage Account Naming Rules (Exam Classic):
  • 3 to 24 characters in length
  • Lowercase letters and numbers only — NO uppercase, hyphens, underscores, or spaces
  • Must be globally unique across all of Azure (it becomes a public DNS subdomain)

05. Access Tiers & Rehydration — Matching Cost to Data Temperature

Data has a "temperature" — how frequently it is accessed over its lifetime. Azure offers four access tiers to balance storage costs against access fees based on data temperature.

Tier Storage Cost Access Cost Min Retention Availability Best For
HotHighestLowestNone99.9%Active daily files, streaming assets, live websites
CoolLowerModerate30 days99%Monthly reports, infrequently accessed customer data
ColdVery LowHigh90 days99%Quarterly backups, regulatory data rarely accessed
ArchiveRock BottomHighest (+ rehydration)180 daysOfflineLegal compliance archives, 7-year tax records
Archive Tier Rehydration: Blobs in Archive tier are stored offline on magnetic tape-equivalent infrastructure. To read an archived blob you must first rehydrate it back to Hot or Cool tier. Standard Priority rehydration takes 1–15 hours. High Priority takes under 1 hour (for blobs under 10 GB) but costs significantly more. You cannot read an archived blob in-place — there is no such thing as instant archive access.

06. Redundancy Theory — Durability at Different Failure Scopes

Azure automatically maintains multiple copies of every blob. The redundancy strategy you choose determines where those copies are stored and therefore what failure scenarios they protect against.

Failure Scope Hierarchy (smallest to largest): Disk failure → Protected by: ALL redundancy tiers Rack failure → Protected by: LRS (3 copies across racks in 1 datacenter) Datacenter fire → Protected by: ZRS (3 copies across 3 Availability Zones) Regional disaster → Protected by: GRS (3 copies in 2nd geographic region) Multi-zone + regional → Protected by: GZRS (ZRS primary + GRS secondary)
Strategy Copies Geographic Scope Annual Durability
LRS (Locally Redundant)3 synchronous copies1 datacenter, different racks11 nines (99.999999999%)
ZRS (Zone Redundant)3 synchronous copies3 Availability Zones, 1 region12 nines
GRS (Geo Redundant)3 primary + 3 secondary async2 geographic regions (paired)16 nines
GZRS (Geo-Zone Redundant)3 zone copies + 3 geo copies3 zones in primary + 2nd region16 nines
RA-GRS / RA-GZRS (Read-Access variants): GRS replicates data to the secondary region but does NOT allow you to read from it during normal operation. RA-GRS provides a read-only endpoint at the secondary region (URL suffix: -secondary.blob.core.windows.net) so your app remains readable even during a full primary region outage.

07. Security: Access Keys, SAS Tokens & Entra ID

Mechanism What It Is Risk Level Best Practice
Account Access Keys512-bit symmetric keys (Key1 + Key2). Like a root password — grants full control over the entire storage account.⚠ Critical RiskNever embed in code or commits. Store in Azure Key Vault only. Rotate regularly.
SAS TokenA URL query string signed with the Account Key. Grants scoped, time-limited access to specific resources and operations.🛡 ControlledIdeal for temporary download links, client uploads, third-party integrations.
Microsoft Entra ID (RBAC)Identity-based role assignment. The user/service proves identity to Entra ID and Azure validates permissions via RBAC role lookup.🔒 Enterprise Best PracticeUse for all production apps, Managed Identities, and VM-to-storage access patterns.

SAS Token Anatomy — What's Inside a SAS URL?

https://mystorage.blob.core.windows.net/images/logo.png ?sv=2023-01-03 ← Storage service version &ss=b ← Services: b=blob &srt=o ← Resource type: o=object (specific blob) &sp=r ← Permissions: r=read only &se=2026-11-18T18:00Z ← Expiry: access dies at 6 PM UTC &sip=203.0.113.0/24 ← Allowed IP range (optional) &spr=https ← Protocol: HTTPS only &sig=abc123...xyz ← HMAC-SHA256 signature (tamper-proof)

If anyone modifies even one character of the URL parameters, the signature verification fails and Azure returns 403 Forbidden — the SAS token is cryptographically tamper-proof.

08. Static Website Hosting on Blob Storage

Azure Storage allows you to host an entire static website (HTML, CSS, JS, React/Vue production builds) directly from a special container named $web without any web server, VM, or App Service plan. The endpoint uses Azure's global CDN infrastructure.

Storage Account: myportfolio2026 └── $web container (special magic container) ├── index.html ← Served at / and /index.html ├── 404.html ← Custom error page ├── styles.css └── app.js Public endpoint: https://myportfolio2026.z13.web.core.windows.net/ ↑ Zone-specific CDN edge node identifier
Free HTTPS included: The .web.core.windows.net domain comes with a free TLS/SSL certificate managed by Microsoft. For a custom domain (e.g., www.yourname.dev), you can use Azure Front Door or Azure CDN to map it, which also adds global caching and DDoS protection.

09. Lifecycle Management Rules — Automated Cost Optimization

Lifecycle Management Rules are JSON-based policies that automatically move or delete blobs based on their age or last access time — no manual intervention required. Azure evaluates rules once per day.

{
  "rules": [{
    "name": "AutoTierLogs",
    "enabled": true,
    "type": "Lifecycle",
    "definition": {
      "actions": {
        "baseBlob": {
          // Move to Cool after 30 days of no modification
          "tierToCool": { "daysAfterModificationGreaterThan": 30 },
          // Move to Archive after 90 days
          "tierToArchive": { "daysAfterModificationGreaterThan": 90 },
          // Delete permanently after 365 days
          "delete": { "daysAfterModificationGreaterThan": 365 }
        }
      },
      "filters": {
        "blobTypes": ["blockBlob"],
        // Only applies to blobs in the "logs/" virtual directory
        "prefixMatch": ["logs/"]
      }
    }
  }]
}

10. Essential CLI Cheatsheet

Create Account & Container

az storage account create   --name mystorageak2026   --resource-group my-rg   --sku Standard_LRS   --kind StorageV2

az storage container create   --account-name mystorageak2026   --name project-assets   --auth-mode login

Upload & SAS Token

az storage blob upload   --account-name mystorageak2026   --container-name project-assets   --name logo.png   --file ./images/logo.png

az storage blob generate-sas   --account-name mystorageak2026   --container-name project-assets   --name logo.png   --permissions r   --expiry 2026-12-01T00:00Z   --full-uri

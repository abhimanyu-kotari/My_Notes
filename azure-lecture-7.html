Identity & Access Management — Theory, Entra ID & RBAC

Cloud security begins with identity. Before any firewall rule, any network policy, or any encryption key — you must answer two questions: Who is trying to access this resource? (Authentication) and What are they allowed to do? (Authorization). This module covers the full theory: how Microsoft Entra ID manages identities as a cloud directory, why the RBAC permission model uses a three-part formula, how scope inheritance flows down the Azure resource hierarchy, and why Managed Identities eliminate the most dangerous anti-pattern in cloud development — hardcoded credentials.

01. AuthN vs. AuthZ — The Foundational Theory

All of cloud security rests on two distinct processes that are often confused but are fundamentally different operations happening in sequence:

Authentication (AuthN) — "Who Are You?"

The process of verifying the claimed identity of a user, computer, or application. The system asks: "Prove that you are who you say you are."

Methods: Password + username, Multi-Factor Authentication (MFA), OAuth2/OIDC tokens, X.509 certificates, biometrics.

In Azure: Microsoft Entra ID performs authentication and issues a JWT access token.

Authorization (AuthZ) — "What Can You Do?"

Once identity is confirmed, the system checks what actions that identity is permitted to perform and on which resources.

Methods: RBAC role assignments, Azure Policy, Attribute-Based Access Control (ABAC).

In Azure: Azure Resource Manager (ARM) evaluates the authenticated identity's RBAC role assignments at the target resource scope.

The sequence matters: Authentication always happens BEFORE authorization. You cannot check what someone is allowed to do until you have verified who they are. If authentication fails, authorization is never evaluated.

02. Airport Security Analogy

Immigration desk checks your photo and biometrics. This is authentication — confirming your identity is real.

🌹

Once past passport control, your boarding pass defines your seat, lounge access, and gate. This is authorization — your allowed scope.

🛡

03. Microsoft Entra ID — Cloud Identity Directory Deep Dive

Microsoft Entra ID (formerly Azure Active Directory / Azure AD) is Microsoft's cloud-native identity and access management service. It is not the same as on-premise Windows Server Active Directory — it is a cloud-first directory designed for internet-scale authentication using modern protocols (OAuth2, OIDC, SAML 2.0).

The 4 Types of Security Principals in Entra ID

Principal Type What It Represents Real Example Key Properties
UserA human being with an interactive login sessionalice@company.com (developer), bob@company.com (admin)Requires password + optional MFA. Can be internal (member) or external (guest via B2B).
GroupA collection of users (or other groups) managed togetherDevOps-Engineers, Frontend-Team, Cloud-AdminsRBAC roles assigned to a group cascade to all members. Easier to manage than individual assignments.
Service PrincipalA machine identity for applications and automation scriptsGitHub Actions runner, Terraform automation bot, Jenkins CIAuthenticates using a client secret or certificate. Must be rotated manually — this is the security risk of service principals.
Managed IdentityAn Azure-managed machine identity for Azure resourcesAn Azure VM accessing Blob Storage without any passwordNo secrets to manage. Azure automatically rotates certificates. Cannot be used outside Azure.

04. Tenant Architecture Theory

When an organization signs up for Microsoft 365 or Azure, Microsoft creates a dedicated Tenant — a private, isolated instance of Entra ID belonging exclusively to that organization. Think of a tenant as your company's private directory database in Microsoft's cloud.

Microsoft Entra ID Global Infrastructure ├── Tenant: contoso.onmicrosoft.com (Contoso Corp) │ ├── Users: alice@contoso.com, bob@contoso.com │ ├── Groups: DevOps-Team, Finance-Admins │ ├── Apps: Contoso ERP, GitHub Enterprise │ └── Azure Subscriptions: Sub-Production, Sub-Dev │ └── Tenant: fabrikam.onmicrosoft.com (Fabrikam Ltd) ├── Users: carol@fabrikam.com └── Azure Subscriptions: Sub-Main ZERO cross-tenant data leakage. Fabrikam cannot see Contoso's users.
Tenant ID vs. Subscription ID: These are two different concepts. A single Entra ID Tenant can have multiple Azure Subscriptions linked to it (e.g., Production, Development, Sandbox). The Tenant manages identity; the Subscription manages billing and resource grouping. When you run az login, you authenticate to your tenant. When you run az account set, you select which subscription's resources to work with.

05. Managed Identities — Eliminating Credential Sprawl

The most dangerous security mistake in cloud development is embedding credentials inside code:

// ❌ NEVER DO THIS — API keys in source code
const storageKey = "DefaultEndpointsProtocol=https;AccountName=mystorage;AccountKey=abc123..."
// This key is now in your git history FOREVER — even if you delete the commit

System-Assigned Managed Identity

Created automatically and tied to a single specific Azure resource (e.g., one VM). When the VM is deleted, Entra ID automatically deletes the identity.

Use when: One resource, one identity. Simple 1:1 mapping. The resource will never be shared with another service.

User-Assigned Managed Identity

Created as a standalone Azure resource. Can be assigned to multiple VMs, Container Apps, or Functions. When one VM is deleted, the identity persists.

Use when: Multiple resources share the same identity (e.g., 5 worker VMs all need to access the same Storage Account).

How Managed Identity Works at Runtime: 1. Developer deploys VM with System-Assigned Managed Identity enabled 2. Entra ID creates a Service Principal for the VM automatically 3. Azure grants the VM's identity "Storage Blob Data Reader" on the target storage account At runtime inside the VM: 4. App calls: http://169.254.169.254/metadata/identity/oauth2/token (Instance Metadata Service) 5. Azure IMDS returns a fresh JWT access token (valid 1 hour, auto-rotated) 6. App uses the token to call the Blob Storage REST API 7. Azure validates the token signature against Entra ID — grants access NO passwords. NO secrets. NO rotation headaches.

06. Azure RBAC — The Three-Part Permission Formula

Every access decision in Azure RBAC is determined by exactly three components combined into a Role Assignment:

Role Assignment = Security Principal + Role Definition + Scope
Security Principal
WHO gets access
Alice, DevOps-Group, GitHub-Actions-SP, VM Managed Identity
Role Definition
WHAT actions they can perform
Reader, Contributor, Owner, Storage Blob Data Reader
Scope
WHERE the permission applies
Management Group, Subscription, Resource Group, or specific Resource
Practical Example: "Alice (principal) has the Contributor role (role) on the rg-ecommerce-prod resource group (scope)." This means Alice can create, modify, and delete any resource inside rg-ecommerce-prod — but has zero permissions on any other resource group or subscription.

07. Scope Hierarchy & Permission Inheritance

[1. Management Groups] ← Organizational governance across subscriptions │ Assign: Azure Policy, Compliance Standards │ Permissions set here apply to ALL child subscriptions ▼ [2. Subscriptions] ← Billing boundary and high-level access control │ Assign: Billing Administrators, Cost Management │ Permissions set here apply to ALL child resource groups ▼ [3. Resource Groups] ← Project lifecycle container (recommended RBAC level) │ Assign: Developer access per project │ Permissions set here apply to ALL resources in the group ▼ [4. Individual Resources] ← Finest grain (specific VM, Storage Account, etc.) Assign: Emergency break-glass access or service-to-service identity
Inheritance Rule Example
Parent permissions flow downReader on Subscription → Reader on every Resource Group and Resource within it
Deny overrides AllowIf Deny Assignment blocks deletion, even Owner cannot delete that resource
Least Privilege best practiceGrant access at Resource Group level, not Subscription level, to limit blast radius

08. Built-In Roles & Data Plane Roles

Role Read Create/Update/Delete Grant Access Ideal For
Owner✓✓✓Cloud admins and subscription owners. Full power including IAM management.
Contributor✓✓✗Developers and DevOps engineers. Full resource management, cannot touch IAM.
Reader✓✗✗Auditors, interns, monitoring tools. Read-only view of resources and configuration.
User Access Admin✓✗✓Security officers who manage role assignments but cannot touch resource configurations.
Control Plane vs. Data Plane — The Critical Distinction:
The Contributor role on a Storage Account lets you change firewall rules, modify the account configuration, and even delete the entire storage account. But by default, it does NOT allow you to read the files inside containers. That is the data plane. To access blobs, you need separate data-plane roles:
Storage Blob Data Reader — read blobs
Storage Blob Data Contributor — read, write, and delete blobs
Key Vault Secrets User — read secrets from Key Vault
Privileged Identity Management (PIM): In production enterprise environments, you should never have standing Owner or Contributor permissions. PIM (a premium Entra ID feature) enables Just-In-Time (JIT) access — a developer requests elevated permissions for a 4-hour window, a manager approves it, and Azure automatically revokes the permissions when the timer expires. This follows the Zero Trust security model: "assume breach, verify explicitly, use least privilege."

09. Step-by-Step Role Assignment in Azure Portal

Azure Portal → Target Resource Group (e.g., rg-ecommerce-prod) └── Left Menu: "Access control (IAM)" └── Tab: "Role assignments" → see all current assignments └── Button: "+ Add" → "Add role assignment" └── Step 1 — Role: Search "Contributor" → Select → Next └── Step 2 — Members: "Assign access to" = User, group, or service principal Click "+ Select members" → search alice@company.com Select → Next └── Step 3 — Review + assign → Review Principal + Role + Scope Click "Review + assign" ✓ Permission active within seconds

10. Essential CLI Commands for IAM

List & Assign Roles

az role assignment list   --resource-group my-rg --output table

az role assignment create   --assignee "alice@company.com"   --role "Contributor"   --resource-group "my-rg"

Managed Identity Assignment

az role assignment create   --assignee-object-id "<managed-identity-id>"   --role "Storage Blob Data Reader"   --scope "/subscriptions/<sub>/resourceGroups/my-rg/providers/Microsoft.Storage/storageAccounts/mystorage"

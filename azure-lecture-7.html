Identity and Access Management (IAM) & Azure RBAC

01. Authentication (AuthN) vs. Authorization (AuthZ)

Cloud security rests upon two distinct, non-negotiable security questions:

Concept The Core Question How It Is Proven Azure Service Responsible
Authentication (AuthN) "Who are you?" Password, biometric fingerprint, FIDO2 security key, 6-digit MFA authenticator code. Microsoft Entra ID
Authorization (AuthZ) "What are you allowed to do?" Permissions attached to your role (e.g. Can you reboot this VM? Can you read this table?). Azure RBAC

02. The Airport Security Analogy

The International Flight:

- Authentication (AuthN): At the immigration counter, the border officer checks your physical passport and verifies your biometric face scan against international records. This proves beyond doubt that you are who you claim to be.

- Authorization (AuthZ): After passing immigration, your passport does not let you open the airplane cockpit door or stroll into the First-Class airport lounge if you hold an Economy ticket! Your Boarding Pass determines your exact Role and Scope.

- Managed Identity: An aircraft mechanic or airline pilot wears an airport RFID badge. They do not memorize 40 individual passwords to open maintenance doors—the airport infrastructure automatically authenticates their authorized role!

03. Microsoft Entra ID Security Principals

Microsoft Entra ID manages four distinct types of identities (Security Principals):

👤
1. Users
Individual humans (e.g. alice@company.com) authenticated with password, MFA, or Passkey.
👥
2. Groups
Collections of users (e.g. DevOps-Engineers) allowing bulk permission grant and revocation.
🤖
3. Service Principals
App identities for automated CI/CD pipelines (GitHub Actions, Jenkins) calling Azure REST APIs.
🛡️
4. Managed Identities
Cloud-native identities for Azure VMs & Containers with automatic credential rotation and zero stored secrets!

04. Managed Identities (Eliminating Hardcoded Passwords)

One of the worst cloud blunders is saving database credentials or storage keys in git code:

❌ THE OLD, DANGEROUS WAY: 
# Hardcoded connection string in app.py
AZURE_STORAGE_KEY = "xK9#8d298374982374987..." # Committed to GitHub → Hacker theft!
✅ THE MODERN MANAGED IDENTITY WAY:

You enable a Managed Identity on your Azure VM or Container App. Azure automatically provisions an identity in Entra ID and injects temporary rotating tokens into the VM metadata endpoint. Your Python app simply asks Azure for a token using DefaultAzureCredential()—no passwords or keys exist anywhere in your codebase!

System-Assigned vs. User-Assigned Managed Identity:

  • System-Assigned: Tied 1-to-1 to a single Azure resource (e.g. 1 VM). If that VM is deleted, Azure automatically deletes the identity.
  • User-Assigned: Created as an independent standalone Azure resource. Can be attached to multiple resources simultaneously (e.g., 10 VMs running the same microservice pool).

06. Scope Hierarchy & Downward Permission Inheritance

AZURE RBAC 4-LEVEL SCOPE HIERARCHY
Level 1: Management Groups
Highest scope; governs multiple Azure subscriptions across the enterprise
Root Scope
↓ (Inherited Downwards)
Level 2: Subscriptions
Billing boundary & cloud account container
Account Scope
↓ (Inherited Downwards)
Level 3: Resource Groups
Logical lifecycle folder for related project resources (Recommended Scope!)
Project Scope
↓ (Inherited Downwards)
Level 4: Individual Resources
Specific VM, Storage Account, Azure SQL Database, Key Vault
Leaf Scope
⚠️ The Law of Downward Inheritance: Permissions granted at a higher level are automatically inherited by all child levels below it!

If you assign someone the Reader role at the Subscription level, they can see every single resource group, virtual machine, and storage account inside that entire subscription. Always follow the Principle of Least Privilege (PoLP): assign roles at the lowest required scope (usually the Resource Group).

07. The 4 Core Built-In Roles

Role Name Read? Create/Update/Delete? Assign Access to Others? Typical Use Case
Owner Yes Yes YES Cloud administrators and lead architects.
Contributor Yes Yes NO Developers & DevOps engineers deploying infrastructure.
Reader Yes No No Auditors, interns, monitoring dashboards.
User Access Admin Yes No (Compute/Disk) YES Security officers managing role assignments without touching servers.

08. Hands-on: Assigning a Role in Azure Portal

1

Navigate to Target Scope

In Azure Portal, open your target Resource Group (e.g., rg-ecommerce-prod) or Subscription.

2

Open Access Control (IAM)

In the left sidebar menu, click Access control (IAM) → Click + Add → Select Add role assignment.

3

Select Role Definition

Under the Role tab, search for and choose Contributor (or your target role) → Click Next.

4

Assign Members

Select User, group, or service principal • Click + Select members • Search for teammate's email (e.g. alice@company.com) → Click Select → Click Next.

5

Review + Assign

Review the scope and role summary → Click Review + assign. The RBAC permission takes effect immediately!

09. Azure CLI Commands for IAM

Azure CLI / Bash 
# 1. List existing role assignments on a Resource Group
$ az role assignment list \
  --resource-group my-rg \
  --output table

# 2. Assign 'Reader' role to a developer on a Resource Group
$ az role assignment create \
  --assignee "alice@company.com" \
  --role "Reader" \
  --resource-group "my-rg"

# 3. Assign 'Storage Blob Data Contributor' to a Managed Identity
$ az role assignment create \
  --assignee-object-id "<vm-managed-identity-guid>" \
  --role "Storage Blob Data Contributor" \
  --scope "/subscriptions/<sub-id>/resourceGroups/my-rg"

# 4. Revoke a role assignment
$ az role assignment delete \
  --assignee "alice@company.com" \
  --role "Reader" \
  --resource-group "my-rg"
